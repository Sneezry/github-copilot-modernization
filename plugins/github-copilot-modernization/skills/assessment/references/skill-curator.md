# Skill Curator — How AI Sediments Team Conventions Into Reusable Skills

> **Purpose**: Let the agent turn recurring patterns ("we always suppress CWE-477 in test code", "internal-libs/* never need CVE updates because they're vendored") into reusable team skills that future runs apply automatically. This is the product's "self-evolution" surface.

> **Inspiration**: Hermes Agent's `skill_manager_tool` + curator system. Same idea, translated to markdown skill instructions.

---

## When the agent proposes a skill

The agent watches for these signals during Step 5 (iteration mode) and Step 6 (sediment):

| Signal | Threshold | Example |
|--------|-----------|---------|
| Repeated suppressions on the same axis | ≥ `preferences.curator_threshold` (default 3) | User added 3 different suppressions all matching `**/internal-libs/**` |
| Repeated acknowledgments of same finding type | ≥ 3 across runs | User acknowledged CWE-477 findings in 3 separate runs |
| Identical user reasons | text match across ≥ 2 transitions | Two findings both annotated `state_reason: "vendored, frozen by security review"` |
| Explicit user instruction | always | User says "remember this for next time" or "make this a rule" |

Threshold is configurable via `preferences.yaml` → `behavior.curator_threshold`. Set to `null` to disable proactive proposals (user can still trigger curator with explicit instruction).

The agent NEVER auto-creates without `ask_user`. See [iteration-playbook.md](iteration-playbook.md) scenario **10**.

---

## What a team skill is (and isn't)

**Is**:
- A small SKILL.md placed at `.github/modernize/.memory/skills/team/<skill-name>/SKILL.md`
- An additional rule that runs alongside the standard assessment-skills
- Auto-loaded by [`SKILL.md`](../SKILL.md) Step 4 if its frontmatter conditions match the current run

**Is not**:
- A replacement for any standard assessment-skill
- A way to modify built-in skill behavior
- A code-execution surface (skills are instructions; the agent interprets them)

**Hard boundary**: AI may write only to `.github/modernize/.memory/skills/team/`. Writing anywhere else (including `.memory/skills/` root or `assessment-skills/`) is forbidden — this is the safety boundary that prevents AI from corrupting the standard catalog.

## SKILL.md template for team skills

```markdown
---
name: team-<short-name>
description: "<one-sentence purpose, action-oriented>"
version: 1
metadata:
  modernize:
    created_by: ai                    # ai | user
    created_at: 2026-05-13T10:42:11Z
    group: <group-id>                 # which group this attaches to
    languages: [java, dotnet, jsts]   # or a subset; "all" allowed
    source_findings:                  # provenance for audit
      - <finding-id-1>
      - <finding-id-2>
      - <finding-id-3>
    source_runs:
      - 2026-05-12T08-00-00Z
      - 2026-05-13T09-00-00Z
    confidence: 0.85                  # 0.0-1.0; agent's self-assessed strength of pattern
    review_required_by: 2026-08-13    # +90 days; force user re-confirmation
---

# <Skill Title>

## Why this skill exists

<2-3 sentences citing the original observations. Reference the `source_findings` IDs.>

## What it checks

<Concrete instructions for the agent. Example:>

When running on this repository, before reporting findings from `cve-known-vulnerabilities`:

1. Identify findings whose `location` matches the glob `**/internal-libs/**`.
2. For each match, set `state` to `suppressed` with `state_reason: "Internal vendored library — version managed centrally per team policy <team-skill-id>"`.
3. Do NOT include these in the summary count of "new" findings.

## When NOT to apply

<Edge cases. Example:>

- If the suppressed CVE has severity `critical` AND is < 30 days old, surface it anyway with a note "Internal lib policy normally suppresses, but a fresh critical merits review."
- If the user explicitly asks "show all CVE findings including internal libs", bypass this rule for the duration of the iteration session.

## Provenance

This skill was generated by the agent on 2026-05-13 after observing 3 manual suppressions matching this pattern. To reset: delete this file or set `state: deprecated` in the frontmatter.

## Effective until

<ISO date — same as `review_required_by` in frontmatter>. After this date, the agent re-asks the user whether the rule still applies.
```

## Lifecycle

1. **Propose** → agent shows the rendered SKILL.md inline; user approves
2. **Create** → write to `.memory/skills/team/<name>/SKILL.md`
3. **Apply** → next `/assessment` Step 4 reads `.memory/skills/team/`, includes matching skills in the run
4. **Renew** → on `review_required_by` date, agent prompts: `"This team skill expires today. Still relevant?"` (Yes / Update / Deprecate)
5. **Deprecate** → user removes or sets `metadata.modernize.state: deprecated`; the file stays in git history

The agent NEVER deletes a team skill. Deprecation is a frontmatter flag.

## Naming convention

```
team-<area>-<specifier>
```

Examples:
- `team-internal-libs-cve-suppress`
- `team-test-cwe-injection-allowlist`
- `team-vendored-licenses`

Rules:
- Always start with `team-` (distinguishes from official skills)
- Lowercase, hyphen-separated
- ≤ 40 chars
- Must be unique within `.memory/skills/team/`; if collision, append `-v2`, `-v3`

## Confidence and review windows

`confidence` is the agent's self-rating. Use this rubric:

| Score | Meaning | Action |
|-------|---------|--------|
| 0.95+ | User explicitly said "make this a rule" with clear scope | `review_required_by: +180 days` |
| 0.80-0.94 | ≥ 3 identical-shape suppressions, no exceptions | `review_required_by: +90 days` |
| 0.60-0.79 | Pattern exists but with some exceptions or ambiguity | `review_required_by: +30 days`, mark as `experimental: true` |
| < 0.60 | Don't propose — not enough signal |

The review window is enforced at Step 1 (load history). Any team skill past its review date is loaded with a warning and the agent surfaces it for re-confirmation in Step 2.

## Auditability

Every team skill MUST include in its frontmatter:

- `created_by: ai` (or `user` if hand-written)
- `created_at`
- `source_findings: [...]` — finding IDs that justified the skill
- `source_runs: [...]` — runs where the pattern was observed

This means every AI-generated rule has a provenance chain. A teammate reviewing `.memory/skills/team/` later can:

1. Read the SKILL.md to understand what it does
2. Look up `source_findings` in `findings.yaml` to see the original observations
3. Look up `source_runs` in `runs/` to see the full context

---

## Conflict resolution

If two team skills produce conflicting state transitions for the same finding (e.g. one says `suppress`, another says `escalate`), the agent:

1. Logs the conflict to `runs/<current>/summary.md`
2. Defaults to the LESS destructive action (`acknowledge` over `suppress`, `escalate` over `acknowledge`)
3. Asks the user during Step 5 to resolve which skill should win — and offers to mark the loser as `deprecated`

---

## What the curator MUST refuse to do

- **Create a skill from a single observation** — patterns require ≥ 3 occurrences (or explicit user "make this a rule")
- **Create a skill that modifies source code** — team skills only change finding STATE, not files
- **Create a skill that increases severity beyond what the original skill produced** — escalation must be human-driven
- **Reference findings that don't exist in `findings.yaml`** — provenance must be valid
- **Write outside `.memory/skills/team/`** — see hard boundary above
- **Create a skill that suppresses ALL findings of a severity** (e.g. "ignore all critical") — that's a policy decision that demands a human approval; respond by asking the user to do it via `suppressions.yaml` directly with explicit reasoning

       Want me to consolidate this into a team skill so future runs handle it
       automatically? Here's what I'd write:

       [renders proposed SKILL.md]

       [ask_user]
